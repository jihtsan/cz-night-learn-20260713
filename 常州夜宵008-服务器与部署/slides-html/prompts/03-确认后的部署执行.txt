二、安全与变更边界

1. 不要覆盖已有配置。修改现有文件前先备份，并记录备份位置。
2. 不要让我把密码、私钥、Token、密钥口令或 .env 内容发送给你。需要敏感信息时，引导我在服务器上安全输入或创建。
3. 未经确认，不要修改 SSH 配置，不要关闭 SSH 端口，不要修改高风险防火墙规则。
4. 不要删除现有容器、镜像、数据卷、数据库、网站配置或日志。
5. 任何需要 sudo、安装软件、开放公网端口、重启现有服务或写入系统目录的步骤，都必须单独说明并等待确认。

三、如果使用 Docker 或 Podman

1. 使用适合项目的官方基础镜像，并固定明确、可维护的版本。
2. 创建 .dockerignore，避免把 .git、依赖缓存、日志、密钥和本地环境文件放进镜像。
3. 在适合时使用多阶段构建，减小运行镜像。
4. 尽量使用非 root 用户运行应用。
5. 添加健康检查、合理的重启策略和资源限制建议。
6. 持久化数据使用独立数据卷或外部托管服务。
7. 不把密码写进镜像、Dockerfile、Compose 文件或 Git 仓库。
8. 数据库、缓存和管理端口默认不公开到公网。

四、如果使用 Docker Compose

1. 应用、数据库、缓存和反向代理使用明确的内部网络通信。
2. 只有确实需要公开的服务映射宿主机端口。
3. 如果使用 Nginx/Caddy，优先只公开 80 和 443；应用端口尽量只在容器网络内部使用。
4. 明确数据卷、健康检查、服务依赖和重启策略。

五、如果使用 Nginx 或 Caddy

1. 配置静态文件或反向代理，并保留服务器上的其他网站配置。
2. 根据项目需要处理 WebSocket、上传大小、代理头和超时。
3. 域名解析确认正确后，再配置 HTTPS。
4. 配置检查通过后再平滑加载，不要直接用重启碰运气。

六、如果使用 Java

1. 可执行 JAR 优先使用合适的 JRE 运行环境。
2. 只有 WAR 项目或项目明确要求时才使用外部 Tomcat。
3. 根据服务器内存设置合理的 JVM 上限，不要默认占用全部内存。

七、分阶段验证

- 项目是否构建成功；
- 镜像是否生成；
- 容器或系统服务是否正常运行；
- 健康检查是否通过；
- 应用内部地址是否可访问；

- 重启策略或开机启动是否有效；
- 回退方法是否实际可用。

如果任何验证失败，停止后续操作，先分析原因。不要通过连续重启、删除数据、扩大权限或关闭防火墙来碰运气。
